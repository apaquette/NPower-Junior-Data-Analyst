## Design a data ingestion solution
- best practice to extract data from source, transform, and load into service layer
- process known as Extract, Transform, Load (ETL) or Extract, Load, Transform (ELT)
- serving layer makes your data available for the service for further data processing
- **data ingestion pipeline**: a sequence of tasks that move and transform data

Common approach for data ingestion
1. Extract raw data from its source
2. Copy and transform the data with Azure Synapse Analytics
3. Store the prepared data in an Azure Blob storage
4. Train the model with Azure Machine Learning

## Features and capabilities of Azure Machine Learning
- a cloud service for training, deploying, and managing ML models
- designed for data scientists, software engineers, DevOps professionals, and others

Azure ML supports tasks:
- Exploring data and preparing it for modelling
- Training and evaluating ML models
- Registering and managing trained models
- Deploying trained models
- Reviewing and applying responsible AI principles and practices

Azure ML provides the following features and capabilities to support ML workloads
- Centralized storage and management for datasets for model training and evaluations
- On-demand compute resources on which you can run ML jobs, including training
- Automated machine learning, which makes it easy to run multiple training jobs with different algorithms and parameters
- Visual tools to determine orchestrated pipelines for processes such as model training or influencing
- Integration with common ML frameworks for easy management of model training, evaluation, and deployment at scale
- Built-in support for visualization and evaluating metrics for responsible AI, including model explainability, fairness assessment, and others

### Decide between compute options
- when using Azure ML to train, you need to select compute
- **Compute**: the computational resources required to perform the training process
- you should monitor how long it takes to train the model and how much compute is used to know whether to scale up or down

| Compute options                                                 | Considerations                                                                                                                                                                                                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Central Processing Unit (CPU) or Graphics Processing Unit (GPU) | CPU is sufficient and cost-effective for smaller tabular datasets. GPU is more powerful and efficient, and can be used for unstructured data (images or text) or larger tabular datasets if CPU compute is insufficient                                                   |
| General purpose or memory optimized                             | Use general purpose to have balanced CPU-to-memory ratio, ideal for testing and development with smaller datasets. Use memory optimized to have high memory-to-CPU ratio. Great for in-memory analytics, which is ideal for larger datasets or when working in notebooks. |
Which compute options fits best is a case of trial and error. You should monitor the compute utilization to understand how much compute resources you're using. If training your model takes too long, you can use GPUs instead of CPUs. Alternatively you can choose to distribute model training by using Spark compute.

# Integrate a model
- should plan how you integrate the model, as it affects how you train the model or what data is used
- You need to deploy a model to an endpoint for integration

## Deploy a model to an endpoint
- goal is to integrate a trained model into an application
- you can use endpoints for easy integrations
- endpoint can be a web address an application can call to get a message

### Get real-time predictions
- when you want the model to score new data as it comes in
- often needed when a model is used by an application such as apps or websites

### Get batch predictions
- for when you want the model to score new data in batches and save results

## Decide between real-time or batch deployment
- How often should predictions be generated?
- How soon are the results needed?
- Should predictions be generated individually or in batches?
- How much compute power is needed to execute the model?

### Identify the necessary frequency of scoring
1. You need the model to score new data as soon as it comes in
2. You can schedule or trigger the model to score the new data you've collected over time
![[Pasted image 20251218131822.png]]
The type of prediction depends on how often and how quickly you need the predictions generated. If you need predictions immediately after data is collected, you need real-time predictions. If the predictions are only consumed at certain times, you need batch predictions.

### Decide on the number of predictions
- **Individually**: The model receives a single row of data and returns whether that individual customer will buy again
- **Batch**: The model receives multiple rows of data in one table and returns whether each customer will buy again

You can generate individual or batch predictions when working with files.

### Consider the cost of compute
- depending on real-time or batch endpoints, different types of computes are needed
- real-time predictions require compute to always be available
- batch predictions need compute to handle large workloads
